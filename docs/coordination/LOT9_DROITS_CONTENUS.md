## Règles effectives et limites

- Une autorisation de présence humaine dans le projet n’est pas une preuve de consentement de chaque personne représentée. L’état API le dit explicitement. Un refus explicite `peopleAllowed:false` prime maintenant sur une ancienne photo marquée avec personne ; sans accord/photo appropriée, la politique native interdit l’ajout de personnes. La vision et la qualité artistique réelles n’ont pas été testées par un fournisseur.
- Les sections HTML/Liquid non fiables ne peuvent activer un script arbitraire dans les thèmes générés/exportés. CSS et animations natives restent admis ; ne pas réécrire la composition pour masquer un refus.
- Un thème importé contenant du code actif conserve son original et ses versions. L’aperçu reste opaque ; un export CMS requiert une revue serveur liée à **l’empreinte exacte de l’archive**, non une déclaration du navigateur. Cette revue ne certifie ni les droits de médias, ni l’innocuité de dépendances tierces.
- Procédure de revue import : opérateur autorisé, copie isolée et inspection des scripts/Liquid/URLs/dépendances, tests sans secrets, licence et périmètre à vérifier ; consigner identité de l’archive, date, périmètre et décision dans le dossier privé. L’autorisation technique `security.importedThemeReviews` est une action d’administration **manuelle**, pas un bouton client ni une configuration activée ici. Toute modification de l’archive invalide l’accord. Aucune archive réelle approuvée dans cette mission.
- Les textes des projets restent des données : ils ne confèrent ni rôle, ni accès à un fichier d’autrui, ni hausse des plafonds. La sécurité n’est pas une promesse que chaque phrase d’un fournisseur est factuellement vraie : le fact-check par métier, les droits et la validation visuelle restent nécessaires.
